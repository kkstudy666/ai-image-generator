# 并发压测报告

## 一、压测目标与范围

本次压测验证「生产级升级」后系统的**接口层并发处理能力**。压测对象为 FastAPI 的 HTTP 接口层（登录、注册、提交任务、历史查询），**不真实调用 Seedream 大模型**（生图单次约 20s 且消耗 API 额度），提交任务接口只验证「写库 + 投递队列」的异步化链路。

## 二、压测环境

| 项 | 值 |
| --- | --- |
| 压测工具 | Locust 2.32.6 |
| 服务端 | FastAPI 0.115.6 + Uvicorn（单进程） |
| 数据库 | SQLite（本地文件） |
| 消息队列 | Redis（本机 6379） |
| 主机 | Windows 11 / Python 3.12.8 |

> 注：为测量接口层「裸吞吐」，压测期间临时调高了限流阈值（`RATE_LIMIT_*`），排除限流对吞吐的干扰。限流保护效果已由冒烟测试单独验证（触发 429）。

## 三、压测参数

- 并发用户数：**100**
- 爬升速率：20 用户/秒
- 持续时间：45 秒
- 各接口权重：提交任务 5 / 历史查询 3 / 登录 1（每次用户启动另有 1 次注册）

## 四、压测结果（优化后）

| 接口 | 请求数 | 失败数 | 成功率 | 平均响应 | 中位数 | P95 | 吞吐(req/s) |
| --- | --- | --- | --- | --- | --- | --- | --- |
| POST /api/generate（提交任务） | 786 | 0 | 100% | 547ms | 98ms | 3.0s | 17.58 |
| GET /api/history（历史查询） | 483 | 0 | 100% | 522ms | 53ms | 3.1s | 10.80 |
| POST /api/auth/login（登录） | 263 | 0 | 100% | 573ms | 450ms | 1.4s | 5.88 |
| POST /api/auth/register（注册） | 100 | 0 | 100% | 6.67s | 6.6s | 13s | 2.24 |
| **聚合** | **1632** | **0** | **100%** | **919ms** | **120ms** | 3.6s | **36.51** |

## 五、结果分析

1. **成功率 100%**：100 并发下 1632 次请求零失败，接口层稳定。
2. **提交任务吞吐 17.58 req/s、中位数 98ms**：体现异步化设计的价值——提交接口只写库 + 投递队列即返回，不等待大模型，支撑高并发提交。
3. **历史查询中位数 53ms**：SQLite 加 `user_id` 索引后分页查询很快。
4. **注册接口平均 6.67s**：这是刻意的安全代价——密码哈希使用 PBKDF2 20 万次迭代防暴力破解，注册是低频操作，可接受。

## 六、优化前后对比

> 说明：原型版本无压测基线且代码已升级，无法回滚实测；下表从**能力维度**对比优化带来的提升，性能数字以优化后实测为准。

| 维度 | 优化前（原型） | 优化后（生产版） |
| --- | --- | --- |
| 并发接口吞吐 | 未测 | 聚合 36.51 req/s，成功率 100% |
| 鉴权 | 无，接口裸奔 | JWT 鉴权 + 多用户数据隔离 |
| 接口防护 | 无 | IP + 用户双维度限流（超限 429） |
| 任务可靠性 | 无重试，worker 崩溃丢任务 | 幂等 + 自动重试（≤2 次）+ 宕机恢复 + 熔断降级 |
| 上传安全 | 仅前端大小判断 | 前端校验 + 后端文件头/大小/格式三重校验 |
| 可观测性 | 无日志 | 分级日志 + 任务 ID 全链路追踪 |

## 七、性能指标总结

- **并发能力**：100 并发稳定运行，零失败。
- **吞吐**：聚合 36.51 req/s；提交任务 17.58 req/s；历史查询 10.80 req/s。
- **响应时间**：提交/历史查询中位数均在 100ms 内（P95 受 SQLite 并发写锁偶发抬升到 3s 左右，属单机 SQLite 的正常表现，量级增大后可迁移 PostgreSQL）。
- **结论**：满足内部小团队使用；若并发再上量级，优先把 SQLite 换成 PostgreSQL、Uvicorn 加多 worker。
